# Поверхность сканирования: что видит активный зонд

**Актуально на:** 04.10.2026.
**Для кого:** для владельца сервера.
**Что это.** Отчёт о том, как сервер выглядит со стороны того, кто его сканирует и «простукивает» снаружи, не зная ключей: активного пробера (ТСПУ, РКН, чужой сканер). Этот документ отвечает на требование владельца №4 про максимальный анти-детект с точки зрения не клиента, а атакующего, и дополняет [RISK-REDUCTION.md](RISK-REDUCTION.md) §5, где те же меры описаны со стороны клиента и утечек IP.

**На чём основано.** Прогон «как цензор» против стенда с включёнными **всеми** протоколами (`ENABLE_TUIC=1 ENABLE_HY2_OBFS=1 HY2_HOP=1`, Ubuntu 24.04, 04.10.2026): полный TCP-скан `nmap -sS -p-`, UDP-зонды (QUIC Initial через aioquic, мусор, рукопожатия), сверка сертификатов и ответов REALITY-портов с настоящими target-сайтами напрямую, повтор перехваченных рукопожатий. Автоматическая часть — [docker/tests/security.sh](../docker/tests/security.sh) (публичные сокеты = реестр портов, служебные порты закрыты, из туннеля сервер изнутри не виден) и [docker/tests/routing.sh](../docker/tests/routing.sh) (анти-утечки через настоящих клиентов). Ручной сканер-прогон в коммит не входит: он описан в разделе «Как повторить» ниже, чтобы владелец мог проверить боевой сервер.

**Главный вывод.** Для сканера без ключей сервер выглядит как набор нескольких высоких портов и обычного 443. Из 65535 TCP-портов открыты только зарегистрированные, остальные — `filtered` (ufw молча роняет пакеты, даже RST не шлёт). REALITY на 443 неотличим от настоящего сайта-прикрытия вплоть до сертификата. Панель, админка, API Xray, метрики, SOCKS-мост TUIC и trafficStats Hysteria доступны только с `127.0.0.1`. Остаточные следы (ниже) — слабые и в основном у протоколов, выключенных по умолчанию.

## 1. Что открыто (полная установка, все протоколы)

Порты высоких протоколов случайны на каждой установке (кроме 443) — в таблице пример со стенда.

| Порт | Протокол | Что видит сканер снаружи | Риск | Что сделано / смягчение |
|---|---|---|---|---|
| **22/tcp** | SSH | Баннер `OpenSSH 9.6p1 Ubuntu`; методы входа `publickey,password` | Перебор паролей; баннер выдаёт ОС (как у любого Linux-VPS) | `ufw limit` + fail2ban (jail `sshd` 5/10 мин, `recidive` неделя). По умолчанию пароли приняты; `SSH_HARDEN=1` переносит SSH на случайный высокий порт и оставляет только `publickey` — см. §3.1 |
| **443/tcp** | VLESS RAW+REALITY+Vision | TLS-сервер, отдающий **настоящий сертификат target** (на стенде `*.lovelive-anime.jp` от Amazon) с доверенной цепочкой; на `GET /` проксирует ответ самого target; на мусор ведёт себя как target | Почти нет: 443 с валидным TLS — самый обычный веб-сервер | REALITY форвардит реальный TLS target (D10); цель выбирает валидатор (TLS 1.3, X25519MLKEM768, h2). `maxTimediff=0` — см. §3.4 |
| **22338/tcp** | VLESS XHTTP+REALITY | То же, но сертификат target `www.cisco.com` **на нестандартном высоком порту** | Лёгкая аномалия: сайт cisco.com на порту ≠443, которого у самого cisco.com там нет | Плата за независимый запасной транспорт (D16). `XHTTP_PLACEMENT=fallback` убирает её (всё на 443) |
| **25104/tcp+udp** | Shadowsocks-2022 | Порт открыт, но **не отдаёт ни байта**; на любые данные ≥1 Б — мгновенный TCP-RST, на пустое соединение — тишина до таймаута | Мгновенный одинаковый RST на мусор любой длины — слабый сигнал для активного зонда | Поведение самого Shadowsocks (без валидной AEAD сервер рвёт). Не-TLS запасной, по умолчанию включён; при подозрении на зонд — `ENABLE_SS=0`. См. §3.3 |
| **443/udp** | Hysteria2 | QUIC-сервер; при ALPN `h3` и SNI `bing.com` завершает TLS (самоподписанный `CN=bing.com`) и **отвечает HTTP/3-маскировкой** — реальным `301` от bing; при другом/пустом SNI рукопожатие QUIC обрывается | QUIC+h3+ответ сайта выглядит как обычный HTTP/3. Остаток: cert самоподписанный; обрыв на чужой SNI | `masquerade: proxy` на `HY2_MASQ_URL`; `sniGuard: dns-san`. См. §3.2 |
| **32109/udp** | TUIC v5 *(выкл. по умолчанию)* | QUIC с ALPN `h3` завершает TLS и отдаёт **самоподписанный сертификат `CN=<IP сервера>`** | Самоподписанный cert на IP — явный признак «не настоящий сайт» для активного QUIC-зонда | `ENABLE_TUIC=0` по умолчанию. Включать только при необходимости. См. §3.5 |
| **24603/udp** | Hysteria2 Salamander (obfs) *(выкл.)* | **Полная тишина**: без правильного пароля obfs QUIC Initial не распознаётся, ответа нет | Минимальный: порт неотличим от закрытого UDP | `obfs: salamander` — лучший анти-зонд из всех (QUIC Initial не виден SNI-фильтру). `ENABLE_HY2_OBFS=1` |
| **27631/udp** | AmneziaWG | **Полная тишина**: пакет без верного ключа/обфускации молча отбрасывается | Минимальный | Уникальные параметры обфускации на установку (D4) |
| hop-диапазон (напр. 40000-49999/udp) | Hysteria port hopping *(опц.)* | DNAT на основной порт Hy2; каждый порт ведёт себя как 443/udp | Широкий диапазон открытых UDP — сам по себе заметен | `HY2_HOP=1` опционально; nft-redirect, сервис не слушает диапазон |
| **все прочие 65531 TCP** | — | `filtered` — ufw default deny роняет пакет без ответа (ни RST, ни ICMP) | — | `ufw default deny incoming`; порт открывает только фаза-владелец через `fw_allow` |

## 2. Что закрыто от сканера (только `127.0.0.1`)

Проверяется автоматически в [security.sh](../docker/tests/security.sh) (connect снаружи обязан провалиться):

| Сервис | Адрес | Почему важно |
|---|---|---|
| Панель 3x-ui | `127.0.0.1:PANEL_PORT` | Открытая HTTP-панель — перебор паролей, утечка ключей, фактор бана (D6). Доступ только через `ssh -L` |
| Веб-админка `zoo` | `127.0.0.1:7070` (`ZOO_WEB_PORT`) | Токен + только через SSH-туннель |
| gRPC API Xray | `127.0.0.1:62789` | **Без авторизации** (так устроен 3x-ui): локальный процесс добавит inbound. Снаружи и из туннеля (D25) — недоступен |
| Метрики Xray | `127.0.0.1:11111` | Статистика трафика без авторизации |
| SOCKS-мост TUIC→Xray | `127.0.0.1:640xx` | **noauth** (хардкод 3x-ui): открытый прокси в Xray для локального процесса. Снаружи закрыт |
| trafficStats Hysteria | `127.0.0.1:2274x/3031x` | Учёт трафика с секретом |

Все перечисленные носят метку «без авторизации, но только loopback»: на одноарендном VPS без посторонних пользователей это приемлемо, снаружи и из VPN-туннеля (D25) они недостижимы. Проверено: `ss` на сервере не показывает ни одного из них на `0.0.0.0`.

## 3. Остаточные следы и их обоснование

### 3.1 SSH принимает пароли, разрешён вход root (по умолчанию)
Без флага сканер видит `publickey,password` и `PermitRootLogin without-password` (на стенде — дефолт образа): **по умолчанию инсталлер SSH не трогает**, потому что ошибка в правке SSH отрезает владельцу единственный вход. Защита от перебора — `ufw limit` + fail2ban.

**Закрыть — флагом `SSH_HARDEN=1` (фаза 01b, D30).** Результат: SSH на случайном высоком порту (или `SSH_PORT=N`, `SSH_PORT=keep` — порт прежний), методы входа — только `publickey`, `PermitRootLogin prohibit-password` (`no` остаётся `no`), `MaxAuthTries 3`, `LoginGraceTime 20`, `X11Forwarding no`; проброс портов (`ssh -L` к панели и админке) оставлен. Старый порт после подтверждения не слушается и закрыт в ufw, то есть для сканера `filtered`, как любой закрытый порт. Риск потерять доступ снят двумя шагами: сначала sshd слушает оба порта и взводится таймер отката, а старый порт закрывается только после подтверждения из новой сессии на новом порту, пришедшей снаружи (не через VPN этого сервера: такая сессия файрвол хостера не проходит). `SSH_HARDEN=0` закрывает порт фазы так же — только после входа на исходный порт. Без подтверждения через 10 минут (`SSH_REVERT_MIN`) всё возвращается само, в том числе после перезагрузки. Порядок действий — README, «Закрыть SSH»; проверка — [docker/tests/ssh-harden.sh](../docker/tests/ssh-harden.sh) на 22.04 (`ssh.service`) и 24.04 (`ssh.socket`).

Что флаг не меняет: баннер `OpenSSH … Ubuntu` и сам факт SSH видны на любом порту, полный `nmap -p-` найдёт его и на высоком. Перенос убирает шум ботов, которые стучатся только на 22, а отказ от паролей закрывает перебор. От целевого скана SSH не прячется, и это не нужно: SSH есть на любом сервере и VPN не выдаёт.

### 3.2 Hysteria2: обрыв QUIC на «неправильном» SNI
С верным SNI (`HY2_SNI`, по умолчанию `bing.com`) и ALPN `h3` сервер маскируется под сайт и отдаёт его ответ. С пустым или чужим SNI рукопожатие QUIC обрывается (`sniGuard: dns-san`). Настоящий HTTP/3-сайт тоже требует своё имя, так что сам по себе обрыв не выдаёт VPN, но самоподписанный `CN=bing.com` при успешном рукопожатии от bing не ждут. Для случая, где это критично, есть **Salamander** (§1, 24603/udp) — он не отвечает вообще. Это сознательный баланс: маскировка под реальный сайт против полной тишины.

### 3.3 Shadowsocks-2022: мгновенный RST
На любой мусор ≥1 Б сервер рвёт соединение немедленно и одинаково (длина не влияет), на пустое соединение молчит до таймаута. Повтор перехваченного трафика (replay) сервер отбрасывает (AEAD-таймстемп 2022-blake3). Одинаковая мгновенная реакция — слабый сигнал для зонда, но это штатное поведение Shadowsocks, менять его в рамках 3x-ui нельзя. SS-2022 — не-TLS запасной канал; при активном зондировании провайдером его стоит выключить (`ENABLE_SS=0`) и опираться на REALITY/Hysteria.

### 3.4 REALITY `maxTimediff=0`
Окна проверки метки времени нет (как в дефолте 3x-ui). Это осознанный выбор, не меняли. На неотличимость от target для пассивного сканера не влияет: до отправки верного REALITY-рукопожатия сервер ведёт себя как сам target.

### 3.5 TUIC: самоподписанный сертификат на IP
При `ENABLE_TUIC=1` активный QUIC-зонд с ALPN `h3` завершит TLS и получит `CN=<IP>` — явный «не сайт». Ссылка клиента использует `allow_insecure=1` без пина (пинит только пробник). Поэтому TUIC **выключен по умолчанию** (D5) и задокументирован как компромиссный протокол. `TUIC_SNI=домен` даёт SAN с именем, но cert всё равно самоподписанный.

### 3.6 XHTTP REALITY на нестандартном порту
Сертификат `www.cisco.com` на высоком порту, которого у cisco там нет, — лёгкая аномалия (D16). Устраняется `XHTTP_PLACEMENT=fallback` (XHTTP прячется за 443 того же VLESS-инбаунда ценой зависимости от фазы 04).

## 4. Сверка с заявлениями RISK-REDUCTION / DECISIONS

| Заявление | Проверка снаружи | Итог |
|---|---|---|
| Панель только на `127.0.0.1` (D6) | connect на `PANEL_PORT` снаружи — отказ | подтверждено |
| Публичная и JSON-подписка выключены (D8) | `subEnable=false`, `subListen=127.0.0.1`, порт подписки не слушает | подтверждено |
| Порты случайные высокие, никогда 1080/3128/8080/9050/2053/54321 | ни один выбранный порт не из `BANNED_PORTS` | подтверждено |
| Из туннеля сервер «изнутри» не виден (D25) | security.sh: из каждого туннеля loopback и адреса сервера (кроме SSH) недоступны | подтверждено |
| echo не отдаёт IP сервера (D9) | routing.sh: `api.ipify.org`/`ip.mail.ru` через туннель заблокированы или через WARP; для AWG (L3) — не закрыто, как и заявлено | подтверждено (AWG — заявленное исключение) |
| REALITY неотличим от сайта-прикрытия (D10) | cert, цепочка, ответ на `GET /` и на мусор совпадают с target напрямую | подтверждено |
| Уникальные параметры AWG (D4) | 27631/udp молчит на чужой пакет | подтверждено |
| access-лог Xray выключен (`access: none`) | в конфиге Xray `log.access="none"` | подтверждено |

Расхождений с заявлениями не найдено. Единственное место, где документация и реальность расходились по тону, — SSH. Теперь его закрывает флаг `SSH_HARDEN=1` (§3.1).

## 5. Как повторить на боевом сервере

Сканер-прогон не входит в обычный e2e (нужен отдельный привилегированный контейнер). Повторить снаружи, с машины в той же сети или из интернета:

```bash
# полный TCP-скан: открыты только зарегистрированные порты, остальные filtered
nmap -n -Pn -sS -p- --min-rate 1000 <IP-сервера>

# REALITY отдаёт сертификат сайта-прикрытия (сравнить с сайтом напрямую)
echo | openssl s_client -connect <IP>:443 -servername <VLESS_SNI> 2>/dev/null | openssl x509 -noout -subject -issuer
echo | openssl s_client -connect <VLESS_SNI>:443 -servername <VLESS_SNI> 2>/dev/null | openssl x509 -noout -subject -issuer

# служебные порты закрыты снаружи, из туннеля сервер изнутри не виден — автоматически:
bash docker/tests/security.sh <контейнер-стенда>      # на стенде
```

На стенде всё это уже закрывают `docker/tests/security.sh` и `docker/tests/routing.sh` (входят в `docker/test.sh --tests all`). Главный остаток, который решает владелец, — SSH-пароли: закрываются флагом `SSH_HARDEN=1` (§3.1, проверка — `docker/tests/ssh-harden.sh`).
