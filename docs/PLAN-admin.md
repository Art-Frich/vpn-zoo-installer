## 1. Метрики на карточках протоколов

**Цель:** на каждой карточке «Обзора»: задержка, джиттер, скорость с сервера, ↑/↓ за сегодня,
«раз в 10 мин · N мин назад ⟳».

**Нагрузка — главное ограничение.**
- Лёгкий замер (раз в 10 мин): на каждый протокол handshake + 5 маленьких запросов через
  туннель → p50 задержки и джиттер (средний модуль разности соседних RTT). Трафик — килобайты.
- Скорость (раз в час, не чаще): загрузка ~1 МБ через туннель. 7 протоколов × 1 МБ × 24 =
  ~170 МБ/сутки — принять или сделать 512 КБ; цифру трафика измерить после деплоя.
- Протоколы — последовательно, не параллельно (CPU всплеск ≤ пары секунд); юнит с `Nice=10`,
  `CPUQuotaPeriod`/`CPUQuota=30%`, `TimeoutStartSec`.
- Источник истины — существующий `zoo probe --local` (учётка zoo-probe). Добавить режим
  `--quick` (без скачивания) и `--speed` (с ним), не писать отдельный пробник.

**Хранение:** таблица в probe-history SQLite: `live (ts, proto, ok, rtt_ms, jitter_ms, mbps NULL, verdict)`,
хранить 7 дней, prune в том же запуске. В экспорт history/ **не** попадает (это не данные клиента).

**Systemd:** `zoo-live.timer` (`OnBootSec=2min`, `OnUnitActiveSec=10min`, `RandomizedDelaySec=30`)
+ `zoo-live.service` (oneshot, `zoo live run`); скорость — по метке времени последнего
speed-замера в meta (≥ 55 мин), отдельный таймер не нужен. Добавить в enable.list.

**Трафик ↑/↓:** коллектор уже пишет байты по протоколам — взять сумму за сегодня по
направлениям (проверить, что направления хранятся раздельно; если нет — добавить поле).
Служебного zoo-probe исключать (иначе замеры скорости раздуют «сегодня»).

**Веб:**
- Карточка: строка метрик `23 мс · ±4 · 38 Мбит/с · ↓1.2 ГБ ↑90 МБ`; цвет точки по свежести
  и вердикту; если замера нет — «нет замера», без нулей.
- Подпись мелко внизу секции: «метрики раз в 10 мин · обновлено 4 мин назад».
- ⟳ на карточке: `POST /live/<proto>` (CSRF) → `systemctl start zoo-live@<proto>`?
  Нет: веб работает с ProtectSystem и без прав на systemctl. Решение: веб пишет файл-заявку
  в `/var/lib/vpn-zoo/live-req/<proto>` + `zoo-live.path` (PathChanged) запускает замер.
  Rate-limit: не чаще 1 раза в 60 с на протокол (проверка mtime заявки и последнего замера).
  Карточка показывает «меряю…», live-обновление подхватит результат.

**Тесты:** unit — расчёт джиттера, prune, выбор «пора ли speed»; web — карточка с данными и
без; docker — таймер отработал, запись в live появилась, ⟳ создаёт заявку и даёт результат.

**Сделано (D39):** `zoo live run|show`, `probe/live.py`, юниты `zoo-live.timer/.service/.path`, `zoo-live-req.service`; тесты — `zoo/tests/test_live.py` и `docker/tests/live.sh`. Открытый вопрос про цель скорости решён: внешний CDN (`speed.cloudflare.com`) через туннель, подпись «скорость сервера» — в D39. Скорость — раз в 55+ минут на протокол (метка в `meta`, ключ `live_speed:<протокол>`), заявка ↻ тоже качает, если пора. ↓/↑ без `zoo-probe`: см. D39 (Xray — вычитание байт замеров).

**Открытые вопросы:** куда скачивать в speed-тесте (свой сервер отдаёт файл сам себе через
туннель — меряет CPU шифрования, а не канал). Честнее «скорость с сервера» = скачивание с
внешнего CDN через туннель, но это внешний запрос и зависимость. Решить при реализации;
подписать, что именно меряем.

## 2. Вкл/выкл протокола с карточки

**Поток:** переключатель на карточке → окно «Выключить TUIC? Клиенты по нему перестанут
подключаться» → `POST /protocols/<id>/enable|disable` (CSRF) → заявка-файл
`/var/lib/vpn-zoo/jobs/<uuid>.json` → `zoo-job.path` → `zoo-job.service` (root, вне песочницы
веба) выполняет `config_set ENABLE_X=0/1` + `install.sh --phase <фаза протокола>`.
Статус задачи (queued/running/ok/fail + хвост лога) — в том же каталоге; карточка
показывает «включается…», live подхватит итог.

**Защита:** whitelist id протоколов и фаз (из манифестов, не из запроса); одна задача за раз
(lock); веб не передаёт ничего, кроме id и действия; лог задачи без секретов.
Нельзя выключить последний включённый протокол (иначе владелец теряет доступ) — запрет +
пояснение. SSH и сам веб не трогаются.

**Таблица ENABLE_* ↔ фаза** — вынести в манифест протокола (`phase`, `enable_var`), не
хардкодить в вебе.

**Тесты:** docker — выключить/включить TUIC через заявку, порт закрылся/открылся,
пользователи сохранились, ссылки скрылись/вернулись.

**Сделано (D40):** `protoctl.py` (`zoo job run|list`), `web/protoviews.py`, юниты `zoo-job.path/.service`; `phase`/`enable_var` пишут все `proto-<id>.sh` (запасная таблица `protoctl.STATIC`). После включения — `zoo user sync`. Не сделано: переприменение `07-routing` после включения (install.sh --phase гоняет одну фазу), «последний включённый» считается по манифестам, WARP с карточки не управляется (нет манифеста).

## 8. Журнал атак: поиск и изучение

**Что есть:** `hits(res, ts, source, kind, ip, port, n)` агрегаты по разрешениям,
`ips(ip, first, last, n, cc)`; индекс `hits_ip(res, ip, ts)`. Свободного текста сообщений
нет — поиск по полям, а не по логам.

**Добавить:**
- Поле поиска: IP или префикс (`185.220.`), страна (`cc:NL`), порт (`:22`), сервис (`ssh`).
  Разбор в один SQL с параметрами (никакой конкатенации строк).
- Фильтры-чипы: сервис (ssh/ufw/f2b/hy2/xray/x-ui/web), тип события, период (как сейчас).
- Число строк оставить; плюс «показать ещё» (keyset-пагинация по `(ts, ip)`, не OFFSET).
- Клик по IP → карточка IP: первые/последние/всего, страна, разбивка по сервисам и портам,
  лента событий; ссылка «скрыть этот IP» (ignore-файл) — только с подтверждением.
- Всё состояние в query-строке; навигация без перезагрузки (тот же механизм, что период);
  live-обновление сохраняет фильтр и не сбрасывает «показать ещё» (на развёрнутой
  выдаче live ставится на паузу).
- Индексы при необходимости: `hits (res, ts)`, `hits (res, source, ts)` — проверить EXPLAIN
  QUERY PLAN и время на реальной базе тестового сервера (цель < 100 мс).

**Таблица «Кто» — оставить как есть** (пользователь: «таблица норм»). Не хватает
**справки по методикам**: что значит каждый вид события.
- Бейдж вида события кликабелен → маленькое окно (механизм `[data-dialog]`), плюс «?» у
  заголовка «Кто» → вся справка списком.
- На каждый вид из `journal.KINDS` — 4 коротких строки: *что это*, *опасно ли*, *что уже
  сделала защита*, *надо ли что-то делать*. Текст — в словаре рядом с KINDS (одно место
  правды для CLI и веба), не в шаблоне.
- Черновик:
  - **закрытый порт** — сканер обходит порты в поиске сервисов; фон интернета, у любого
    сервера сотни в сутки. Фаервол молча отбрасывает. Делать ничего не нужно.
  - **лимит подключений SSH** — слишком частые подключения к SSH, ufw притормозил.
  - **перебор SSH** — подбор пароля/ключа. Пароли выключены, вход только по ключу —
    подобрать нельзя; fail2ban банит адрес. Делать ничего, если не растёт лавинообразно.
  - **сканер SSH** — проверяли версию SSH без попытки входа.
  - **бан fail2ban** — реакция защиты, не атака.
  - **Hysteria2: неверный ключ** — к порту Hysteria2 пришли с чужим паролем: активное
    зондирование или клиент со старым ключом. Если адрес свой — обновить ссылку.
  - **REALITY: чужой клиент** — к порту VLESS пришли без нужного ключа; REALITY отдал им
    настоящий сайт-маскировку. Так цензор проверяет «прокси ли это». Единичные — норма,
    лавина с одного адреса — повод сменить порт/SNI (RISK-REDUCTION.md).
  - **вход в 3x-ui / в админку zoo** — попытки входа в панели; панели слушают только
    127.0.0.1, снаружи они недоступны — значит это через туннель/SSH, проверить, свои ли.
- Факты в черновике (пароли SSH выключены? лимит ufw после D37 ещё есть? панели только
  на 127.0.0.1?) — **сверить с кодом перед написанием**, не утверждать по памяти.

**Тесты:** unit — парсер строки поиска, SQL с фильтрами, keyset, справка есть для каждого KINDS; web — фильтр в URL, пустая выдача, инъекция в поиск.

## 10. Журнал, «Что делали»: нули непонятны, детектор REALITY слепой

Проверено на тестовом сервере 2026-10-06:
- **REALITY: детектор не видит ничего — и это решение D32, а не баг.** Xray 26.9.30 пишет
  «REALITY: processed invalid connection» через `errors.LogInfo` (transport/internet/tcp/hub.go:110),
  а на уровне Info Xray пишет и назначения пользователей («default route for tcp:host:port»)
  — против правила «не пишем, куда ходят пользователи». Поэтому loglevel **не поднимаем**;
  разбор строки оставлен для владельца, который поднимет уровень сам. Карточка должна
  говорить «не отслеживается (так задумано: иначе в логах были бы сайты пользователей)»,
  а не 0. Если владелец поднял уровень — считать как сейчас.
- **Hysteria2: детектор исправен** (хук auth на неверный ключ пишет `reject <адрес>`,
  проверено вручную, тестовый адрес 192.0.2.7 — TEST-NET). Но хук вызывается, только если
  клиент прислал ключ: QUIC-сканеры без ключа получают маскировку и в журнал не попадают.
  Ноль здесь честный, но узкий.
- **Входы в панели:** панели слушают 127.0.0.1, снаружи недоступны → ноль ожидаем; карточка
  ловит только неудачные входы через туннель/SSH.

**UI:**
- Карточки с нулём не показывать крупно: одна строка «REALITY, Hysteria2, панели — попыток
  не было».
- Если детектор не работает (как REALITY сейчас) — так и писать: «не отслеживается: …»,
  а не 0.
- Переименовать «Проверяли REALITY и Hysteria2» → «Проверяли, прокси ли это» + справка (п. 8).
- Самопроверка (/probe): «RTT» и «Задержка» дублируют друг друга, «—» и «0 мс» путают —
  оставить одну колонку с понятной подписью.

## 11. «Лучшие протоколы» (/probe, рейтинг): не выглядеть точнее, чем есть

Скриншот 2026-10-06: в каждом блоке по 1 прогону (1/1), задержка одного протокола 339 и

- Пока прогонов < 3: не ставить места 1/2/3 и не считать «оценку»; вместо таблицы-рейтинга —
  «1 замер — ориентир, не рейтинг» и сырые цифры мельче. Плашку «мало данных» — одну на блок,
  а не на каждую строку.
- При ≥ 3: показывать медиану и разброс («95 мс, 80–130»), места — по медиане.
- Формулу оценки убрать из текста под заголовком в «?»-справку. Над таблицей одна строка:
  «по вашим замерам с устройств; мобильная сеть и Wi-Fi — отдельно».
- «—» в колонке «Место» непонятно → «вне топ-3» или пусто.
- Протокол, выключенный на сервере (ss2022), в рейтинге не показывать или серым «выключен»,
  а не «0 / 0%».
- Не смешивать с серверными замерами п. 1: там «работает ли с сервера», здесь «как у
  пользователя».
- Имена протоколов — те же человеческие, что на карточках (п. 7), не id.
- **«Тренды» и рейтинг — строки по всем включённым протоколам сервера**, а не только по тем,
  что есть в истории. Скриншот 2026-10-06: 5 строк вместо 7 — оба клиентских прогона были

  прогонов → строка «нет замеров с устройств — запустите пробу» (ссылка на инструкцию).
  Выключенный (ss2022) — серым внизу, со старыми вердиктами.
- «Тренды» дополняют рейтинг (пользователь: «интересно») — оставить, но связать: одна
  секция «Как работает у пользователей», рейтинг сверху, тренды под ним.

## 12. Общий компонент таблиц: смотреть всё, а не первые N

Пользователь 2026-10-06: «таблиц много, данных много, но управлять ими или банально
просмотреть — нельзя». Касается всех таблиц: история прогонов, журнал (п. 8), тренды,
трафик по пользователям, версии, config.env.

Один компонент вместо разовых решений на каждой странице:
- **Серверная пагинация** keyset (по ts/id), «показать ещё» + число «показано 50 из 1 240».
  Никакого OFFSET и никакой выгрузки всего в HTML.
- **Поиск** (одно поле) и **фильтры-чипы** по колонкам с малым числом значений
  (кто/метка/устройство/вердикт). Состояние — в query-строке; навигация без перезагрузки
  (механизм периода); live сохраняет состояние, на развёрнутой выдаче — пауза.
- **Сортировка** кликом по заголовку (whitelist колонок на сервере, не произвольный SQL).
- **Клик по строке → подробности**: прогон → все протоколы с вердиктами, задержкой,
  джиттером, потерями, скоростью, IP выхода; IP журнала → его карточка (п. 8).
- **Выгрузка** видимой выборки в CSV/JSON (кнопка; без приватных полей там, где выгрузка
  может уйти наружу; IP — только для владельца в локальной админке).
- **Управление** там, где имеет смысл и безопасно: удалить прогон из истории (с
  подтверждением), скрыть IP журнала (ignore), пометить прогон меткой.
- Реализация: один модуль `web/table.py` (описание колонок, парсинг query, SQL-построитель
  с параметрами) + один JS-обработчик. Страницы описывают таблицу, а не верстают её.
- Ширина телефона: колонки второго плана прячутся, остаются в подробностях.

## 14. Без перезагрузок и дёрганий (приложения через VPN и все формы)

Пользователь 2026-10-06: на «Приложения через VPN» кнопка «Показать» грузит, страница
дёргается; «любой современный CSR-фреймворк помог бы».

Причина: каждая форма (выбор списка, «Убрать», «Добавить», период, вкл/выкл пользователя)
— полная перезагрузка страницы → прокрутка в начало, мигание, сдвиг вёрстки.

**Решение — без фреймворка** (D7: stdlib, ноль зависимостей, нет сборки, строгий CSP
`script-src 'self'`; страница сервер рендерит за ~200–300 мс — узкое место не рендер, а
полная перезагрузка):
- Обобщить механизм периода на **все формы и ссылки внутри `main`**: `fetch` → заменить
  только изменившийся блок (`data-swap="#id"`), `history.replaceState`, прокрутка и фокус
  сохраняются. Без JS формы работают как сейчас.
- `<select>` «Чей список» — применять сразу при выборе, кнопку «Показать» убрать.
- «Убрать»/«Добавить» — строка исчезает/появляется на месте, ответ сервера — фрагмент
  таблицы; ошибка — тостом, без перехода.
- Против дёрганий: фиксированные размеры у блоков, которые подгружаются (min-height,
  `scrollbar-gutter: stable`), индикатор загрузки — тонкая полоса, не перекрашивание
  `main`.
- Замер: время от клика до обновления (DevTools) до/после на 3 страницах.

**Если интерактива станет много** (таблицы п. 12, переключатели п. 2, live п. 9) и
самописный JS перевалит за ~600 строк — пересмотреть: Preact + htm (≈5 КБ, без сборки,
вендорится в assets, CSP не меняется). Решение записать в DECISIONS.md, когда дойдём.

## 15. «Приложения через VPN»: понятное управление

Пользователь 2026-10-06: «сложновато… не понимаю… селекты сломались… неинтуитивно,
непонятно как этим управлять».

**Селект не сломан, но выглядит сломанным:** в нём только приложения каталога, которых ещё
нет в списке (`allowviews._platform_card`), а пресет теперь = весь каталог → в селекте один
заголовок «— из каталога —».

**Что непонятно сейчас:** отдельные списки Android/Windows с ID в первой колонке; «Чей
список» + кнопка «Показать»; добавить — через пустой селект или ручной ID; абзац правил
сверху, который никто не прочтёт.

**Переделка:**
- **Одна таблица по приложениям, а не по платформам:** строка = приложение
  («Telegram»), справа два переключателя `Android` `Windows`. Включил — идёт через VPN.
  ID (com.brave.browser / brave.exe) — мелко серым под названием или в подсказке.
- Весь каталог всегда виден (включённые и выключенные) → нечего «добавлять из селекта»,
  селект убрать. Группы каталога (мессенджеры, браузер, соцсети, ИИ) — подзаголовками.
- «Своё приложение» — свёрнутый блок внизу: название + ID Android и/или Windows, с
  подсказкой, где взять ID.
- **Чей список:** сегменты «Общий · owner · masha»; у пользователя пометка «как общий» /
  «свой (отличается: +2 −1)» и кнопка «сбросить к общему». Применяется сразу (п. 14).
- Текст сверху — одна строка: «Через VPN идут только отмеченные приложения, остальное —
  напрямую (банки, Госуслуги, MAX)». Остальное — в «?».
- **После изменения** — плашка вместо абзаца: «Список изменён — пользователям нужен новый

  приложение платформы — переключатель неактивен с подсказкой.
- Переключатель — `<button>` в форме (работает без JS), с JS — на месте без перезагрузки.
- **Черновик + одно сохранение** (пользователь: «мне чтобы 1 список составить так
  страдать?» — сейчас каждый клик = пересборка файлов всем пользователям + перезагрузка +

  прокрутки.
