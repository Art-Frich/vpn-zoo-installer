| D30 | Закрытие SSH (`SSH_HARDEN=1`, фаза 01b) — только по флагу и в два шага: (1) sshd слушает старый и новый порт, пароли и root по паролю выключены, взведён таймер отката (до первого изменения: шаг 1, оборванный на середине, тоже откатится); (2) подтверждение из SSH-сессии на новом порту закрывает старый (sshd, ufw, fail2ban). Без подтверждения таймер (10 минут, `SSH_REVERT_MIN`) возвращает снимок `/etc/ssh` и прежние ufw/fail2ban и пишет `SSH_HARDEN=0`, чтобы следующий `install.sh` не повторил шаг сам | По умолчанию не трогаем: ключа у владельца может не быть (ключ из панели хостера потерян), у хостера может быть свой файрвол на 22, и любая ошибка отрезает единственный вход. Наличие ключа в `authorized_keys` (проверка до изменений) не доказывает, что у владельца есть приватный ключ, — доказательство только успешный вход: сессия на новом порту (пароли к этому моменту выключены) или, при `SSH_PORT=keep`, вход по ключу по журналу sshd. Сессия определяется по дереву процессов (под `sudo` `SSH_CONNECTION` нет). Сессия с адреса самого сервера или через его туннель (loopback, свой адрес, интерфейс без L2) доказательством не считается: так приходит вход через VPN этого же сервера и `ssh -J` по старому порту, а файрвол хостера он не проходит. Если закрываются другие порты, сессия обязана быть на новом порту, даже когда он был и до шага 1 (`SSH_PORT=keep` или порт из `SSH_PORTS`). `SSH_HARDEN=0` при сменённом порту — тоже в два запуска: сначала исходный вход и оба порта, затем порт фазы закрывается из сессии на исходном порту. Иначе возврат на 22 за файрволом хостера, пропускающим только новый порт, отрезал бы доступ, и таймер бы не помог. Пока шаг 1 ждёт подтверждения, адрес владельца в fail2ban — в `ignoreip` (в памяти fail2ban), чтобы пробы ключей при `MaxAuthTries 3` не забанили его на час. `install.sh --phase 01b` держит блокировку; прямой запуск `01b-ssh.sh` берёт её сам, чтобы откат не пошёл посреди подтверждения. Таймер — юнит в `/etc/systemd/system` с `OnActiveSec`, а не `systemd-run`: переживает перезагрузку (после загрузки отсчёт заново), пока работает `install.sh` — откладывается. На 24.04 порт задаёт `Port` в drop-in `00-vpn-zoo.conf`, а `ssh.socket` строит штатный `sshd-socket-generator` (учитывает `ListenAddress`); свой drop-in сокета — только где генератора нет. Чужие строки `Port` комментируются меткой (Port в sshd накапливается из всех файлов). `MaxAuthTries 3`: при четырёх и больше ключах в агенте нужен `-o IdentitiesOnly=yes -i` (это есть в инструкции) | `SSH_HARDEN=0` — исходные порт и настройки sshd; `SSH_PORT=N\|random\|keep`; `SSH_CONFIRM_FORCE=1` — подтвердить из консоли хостера |
| D31 | Режим по умолчанию — allowlist («обратный сплит»): через VPN только приложения из списка, всё остальное мимо. Один реестр `/etc/vpn-setup/allowlist.json` (пресет `scripts/allowlist-default.json` — весь каталог `zoo allow`: перевыпустить QR потом трудно, лишнее пользователь снимет сам; в каталоге только зарубежные сервисы), свой список у пользователя по желанию. Из него — Android-вариант AWG `amneziawg-android.conf` с `IncludedApplications` (общий `.conf` без ключа) и правила v2rayN `v2rayn-routing.json` | Новые, забытые и предустановленные приложения, в том числе все RU-приложения, по умолчанию не видят адрес сервера; при «исключить RU» любое забытое шло в туннель. Пресет короткий: меньше приложений в VPN — меньше каналов утечки. Пакет, которого нет на телефоне, по коду AOSP пропускается (`verifyApp` не бросает исключение), туннель поднимается — на телефоне не проверено (RISK-REDUCTION §7). Ключ — только в Android-варианте: awg-quick (пробник), iOS и десктоп его не знают. Без домена и публичной подписки серверу доступны только QR/файлы, заголовки INCY — позже | `zoo allow add\|del\|reset [--user ИМЯ]`, админка → «Приложения»; пресет — `scripts/allowlist-default.json` |
| D32 | Журнал атак «Кто нас щупал» (`zoo journal`, админка → «Атаки», `journal.sqlite` рядом с `traffic.sqlite`): источники — только журналы, которые сервер уже пишет, без новых исходящих соединений: sshd, fail2ban, блокировки ufw из журнала ядра (`ufw logging low`, включает фаза 01, если лог был выключен), неверный ключ Hysteria2 (строку «reject IP:порт» пишет помощник `hy2-auth` через `logger`), неудачные входы 3x-ui и zoo-web. Храним адрес источника, порт назначения, вид и счётчик (по часам 8 суток, по суткам 90); трафик и назначения пользователей, имена, пароли и строки журнала не храним, пакеты с VPN-интерфейсов (`IN=` не внешний) и UDP на порты от 32768 (эфемерные: запоздалые ответы сайтов, куда ходили пользователи, после истечения conntrack — SRC там назначение пользователя) отбрасываем; верный ключ выключенного пользователя Hysteria2 помощник не пишет. Не включаем и не меняем: access-лог и уровень Info у Xray, уровни info/debug у Hysteria, `show` у REALITY. Страна — из `geoip.dat` Xray (уже закреплён D1), ASN нет. Своим считается адрес, с которого был вход по ключу SSH (30 суток), и сети из `/etc/vpn-setup/journal-ignore.txt`; не из публичного интернета (контейнеры, тесты) — «локальный»; оба скрыты, пока нет `--all` | Замеры 05.10.2026 (Xray 26.9.30, Hysteria v2.12.3, стенд 24.04): строка «REALITY: processed invalid connection from IP» пишется на уровне **Info**; на warning чужой клиент REALITY, мусор на SS-2022/XHTTP и неверный ключ Hysteria не оставляют ни строки. На Info в журнал идут и назначения пользователей Xray («default route for tcp:host:port») и в 3xui.log тоже — это против правила «не пишем, куда ходят пользователи» (access-лог выключен по той же причине), поэтому проб REALITY не видим; разбор строки оставлен на случай, если владелец поднимет уровень сам. У Hysteria на error тишина, на info — «client connected {addr, id}» (адреса и имена настоящих пользователей), на debug при неверном ключе — «masquerade request» (и, по документации, запросы пользователей); поэтому отказ пишет помощник авторизации, только адрес. AmneziaWG: amneziawg-go на мусорные UDP молчит (замер); модуль ядра — по коду upstream не логирует по умолчанию (не проверено). ufw пишет блокировки правилом `-m limit --limit 3/min --limit-burst 10` на весь сервер (так в `iptables -S ufw-logging-deny`): число попыток по портам — выборка, адреса видны; запись ≈ 680 байт (journalctl -o export), то есть не больше ≈ 3 МБ в сутки. На стенде LOG из сети контейнера в журнал ядра не доходит, живые «[UFW BLOCK]» не проверены. Наборы вроде iptoasn меняются ежечасно и под sha256-пин не подходят, поэтому ASN нет; индекс стран из geoip.dat (14 МБ) собирается за ≈ 2 с с пиком ≈ 200 МБ RSS при смене файла | Срок хранения — `ZOO_JOURNAL_KEEP_DAYS` (7–365, по умолчанию 90) в окружении коллектора; выключить сбор — убрать `ExecStartPost` из `zoo-collector.service`; лог ufw — `ufw logging off`; сбросить историю — удалить `/var/lib/vpn-zoo/journal.sqlite` |
| D33 | Расширенные метрики пробы — поле `metrics` отчёта, вердикт не меняется: задержка = TTFB малого запроса через туннель (5 замеров на каждую из двух целей — медиана, p90, джиттер, потери), скорость загрузки по тому же большому запросу, объём по умолчанию 5 МБ (`--speed-mb`), отдача — по запросу (`--upload-mb`, POST на `speed.cloudflare.com/__up`). Всё — только через локальный прокси клиента протокола | TTFB отделён от установки соединения и TLS: показывает круг «клиент → туннель → интернет», а не стоимость рукопожатий.
